# ممیزی عمق

سندی که در پاسخ به یک ایراد درست نوشته شد: **کاتالوگ فیچرها محور «عمق» نداشت.**

---

## ۱. ایراد روشی

کاتالوگ [FEATURE-RESEARCH](FEATURE-RESEARCH.md) هر قابلیت را یک ردیف جدول می‌دید.
یک ردیف می‌گوید قابلیت *هست*، ولی نمی‌گوید **در چه کیفیتی**.

نمونهٔ واقعی: «جداسازی سوژه با AI» (P0) و «اصلاح لبه / پرزدهی مو» (P2). هر دو در
کاتالوگ بودند. ولی هیچ‌کدام نمی‌گفت تفاوت بین ماسک باینری و ماتینگ آلفا چیست، و مو
با اولویت **P2** — یعنی «تکمیلی» — ثبت شده بود، در حالی که برای کار شما حیاتی است.

نتیجه: کاتالوگ از این به بعد یک محور دیگر دارد — **سطح کیفیت**.

| سطح | معنی |
|---|---|
| **د** — دم‌دستی | مثل اپ‌های رایگان موبایل. کار می‌کند، ولی حرفه‌ای نیست. |
| **ح** — حرفه‌ای | برای کار واقعی کافی است. اکثر کاربران تفاوتش با فتوشاپ را نمی‌بینند. |
| **ف** — هم‌تراز فتوشاپ | خروجی از فتوشاپ قابل تشخیص نیست. |

هر قابلیت باید سطح هدفش صریح باشد. **هدف پیش‌فرض این پروژه سطح «ح» است، و برای
قابلیت‌های اصلی سطح «ف».**

---

## ۲. نتیجهٔ ممیزی — دو شکاف واقعی پیدا شد

### شکاف ۱ — نور استودیویی روی عکس: **کاملاً غایب بود** ⛔

حق با شما بود. در کل کاتالوگ، «نور» فقط سه جا آمده بود:

- نورپردازی متن سه‌بعدی (`LightRig` در مدل داده) — که ربطی به عکس ندارد
- «نور و های‌لایت» در رتوش پرتره — یعنی روشن‌کردن موضعی، نه نورپردازی
- «نشت نور» به‌عنوان اورلی — یعنی یک تصویر روی عکس

**نورپردازی مجدد یک عکس هیچ‌جا برنامه‌ریزی نشده بود.** این یک قابلیت مستقل و
سنگین است، نه یک اسلایدر:

| سطح | روش | نیاز |
|---|---|---|
| د | اورلی گرادیانی + ماسک روشنایی | همین حالا با موتور فعلی ممکن است |
| ح | نورپردازی با ماسک عمق تقریبی از سگمنتیشن سوژه | مدل سگمنتیشن موجود |
| **ف** | **تخمین نقشهٔ عمق → استخراج نرمال → نورپردازی مجدد فیزیکی** | **مدل عمق روی دستگاه (MiDaS/Depth-Anything سبک)** |

سطح «ف» یعنی همان کاری که فیلتر Lighting Effects فتوشاپ و حالت پرترهٔ گوشی‌ها
می‌کنند: از عکس دوبعدی، نرمال سطح تخمین زده می‌شود و بعد نور مجازی روی آن محاسبه
می‌شود. با نرمال درست، نور روی صورت واقعی به نظر می‌رسد نه مثل یک لکهٔ روشن.

**افزوده شد به کاتالوگ با اولویت P1.**

### شکاف ۲ — فضای رنگ و دقت بیت: **از سند و کد هر دو غایب بود** ⛔⛔

این را خودم پیدا کردم و از شکاف اول جدی‌تر است.

هیچ‌جا تصمیم گرفته نشده بود که ترکیب لایه‌ها در چه فضای رنگی و با چه دقتی انجام
شود. یعنی پیش‌فرض ضمنی **۸ بیت در فضای گاما** بود — همان چیزی که اپ‌های دم‌دستی
می‌کنند.

چرا مهم است:

- **باندینگ.** استایل‌های مرجع شما یک گرادیان را از ۱۰ سایهٔ پشته‌ای و یک پخ عبور
  می‌دهند. هر پاس در ۸ بیت گرد می‌شود. نوارهای رنگی که در تصویر نهایی می‌مانند
  دیگر قابل برگشت نیستند.
- **درخشش و نور اشتباه جمع می‌شوند.** در فضای گاما، دو نور روی هم به‌درستی جمع
  نمی‌شوند. افکت‌های نئونی و شیشه‌ای مصنوعی به نظر می‌رسند.
- **بازنویسی گران است.** اگر ترکیب‌کننده در ۸ بیت ساخته شود، تغییرش بعداً یعنی
  بازنویسی هر شیدر و تغییر ظاهر هر سند ذخیره‌شده.

**همین حالا در کد اصلاح شد** — `core/model/ColorPipeline.kt`:

```kotlin
ColorSettings(
    workingSpace = SRGB | DISPLAY_P3,
    precision    = F16,          // پیش‌فرض؛ نه U8
    blendSpace   = LINEAR,       // فیزیکی درست
)
```

و `BlendSpace.PERCEPTUAL` هم پشتیبانی می‌شود، چون فتوشاپ در فضای گاما ترکیب می‌کند
و برای اینکه یک PSD ایمپورت‌شده **دقیقاً** مثل فتوشاپ دربیاید، راهی جز تقلید آن نیست.

هزینه: دو برابر حافظه. گوشی شما ۱۲ تا ۱۶ گیگ رم دارد — مسئله‌ای نیست.

## ۳. ممیزی کامل دامنه‌ها

### رنگ و گریدینگ

کاتالوگ اینجا **بد نبود** — Levels، Curves با کانال‌های جدا، HSL انتخابی، تعادل رنگ،
رنگ انتخابی، نگاشت گرادیان، LUT. ولی برای سطح «ف» اینها کم بود:

| مورد | وضعیت قبل | اقدام |
|---|---|---|
| فضای رنگ و دقت | غایب | ✅ اضافه شد به کد |
| **اسکوپ‌ها** — هیستوگرام، پرید RGB، ویوفرم، وکتوراسکوپ | غایب | ➕ P1 |
| **Curves با انتخاب از تصویر** (کلیک روی عکس و کشیدن) | غایب | ➕ P1 |
| **دوج و برن غیرمخرب** روی لایهٔ جدا | غایب | ➕ P1 |
| **جداسازی فرکانسی** (رتوش پوست حرفه‌ای) | غایب | ➕ P2 |
| **پنل پایهٔ کمرا-را** (نوردهی، های‌لایت، سایه، سفیدی، سیاهی) | غایب | ➕ P1 |
| **اسپلیت تونینگ** | غایب | ➕ P2 |
| کیفیت درون‌یابی LUT (چهاروجهی نه سه‌خطی) | نامشخص | ➕ جزئیات پیاده‌سازی |

### انتخاب و ماسک

| مورد | وضعیت قبل | اقدام |
|---|---|---|
| ماتینگ آلفا برای مو | P2، بدون جزئیات | ✅ سند [CUTOUT](CUTOUT.md)، ارتقا به P0 |
| رفع آلودگی رنگی | غایب | ✅ در همان سند |
| **ماسک روشنایی** (انتخاب بر اساس بازهٔ تُن) | غایب | ➕ P1 — پایهٔ کامپوزیت حرفه‌ای |
| **انتخاب بر اساس کانال** | غایب | ➕ P2 |
| **حالت ماسک سریع** (Quick Mask) | غایب | ➕ P2 |

### تایپوگرافی

قوی‌ترین بخش، ولی دو مورد کم داشت:

| مورد | وضعیت قبل | اقدام |
|---|---|---|
| **تراز کامل با کشیده** (تراز عربی واقعی) | کشیده بود، تراز نبود | ➕ P1 |
| **کرنینگ نوری در برابر متریک** | غایب | ➕ P2 |
| نقطه‌گذاری آویزان | غایب | ➕ P3 |

مورد اول واقعاً مهم است: در تایپوگرافی فارسی، تراز دوطرفه با **کشیدن حروف** انجام
می‌شود نه با پهن‌کردن فاصله‌ها. موتور کشیده ساخته شده؛ اتصالش به الگوریتم تراز باقی است.

### خروجی

| مورد | وضعیت قبل | اقدام |
|---|---|---|
| جاسازی پروفایل رنگ در خروجی | غایب | ➕ P1 |
| PNG شانزده‌بیتی | غایب | ➕ P2 |
| CMYK | غایب | ❌ **خارج از دامنه** — کار چاپ است، اعلام صریح |

## ۴. جدول سطح کیفیت هدف

| دامنه | سطح هدف | دلیل |
|---|---|---|
| تایپوگرافی فارسی | **ف+** | هدف اصلی؛ از فتوشاپ هم باید بهتر باشد |
| افکت‌های متنی و استایل | **ف** | تمام PSDهای مرجع باید بازتولید شوند |
| موتور لایه و ترکیب | **ف** | زیربنا؛ کوتاه‌آمدن اینجا همه‌چیز را محدود می‌کند |
| جداسازی سوژه و مو | **ف** | خواستهٔ صریح |
| رنگ و گریدینگ | **ف** | کار تولید محتوا به آن وابسته است |
| مدیریت فونت | **ف+** | هیچ اپی این را درست انجام نمی‌دهد |
| نور استودیویی | **ح** ابتدا، **ف** بعداً | مدل عمق لازم دارد |
| رتوش پرتره | **ح** | AirBrush سطح مرجع است، نه فتوشاپ |
| وکتور | **ح** | ایلاستریتور هدف نیست |
| ترمیم و حذف شیء | **ح** | سطح «ف» به مدل‌های ابری نیاز دارد |

## ۵. ماژولار بودن — با کد، نه با حرف

خواستهٔ دوم: «همه‌چیز کامپوننت‌شده و ماژولار باشد.»

### ساختار ماژول‌ها

```
core:model    مدل داده — بدون هیچ وابستگی به اندروید
core:text     متن فارسی — فقط به model وابسته
core:fonts    مدیریت فونت — به model و text
core:render   ترکیب و افکت — فقط به model
```

هستهٔ پروژه عمداً **Kotlin خالص** است. نتیجهٔ عملی: ۱۰۱ تست بدون شبیه‌ساز اجرا
می‌شوند و منطق قبل از رسیدن به دستگاه اعتبارسنجی می‌شود.

### افکت‌ها به‌صورت افزونه

هر افکت یک `EffectModule` است که **همه‌چیز خودش را می‌داند**:

```kotlin
interface EffectModule<E : Effect> {
    val id: String
    val label: String
    val slot: PassSlot                    // جای خود در ترتیب رسم
    val parameters: List<ParameterSpec>   // رابط کاربری از اینجا ساخته می‌شود
    fun bleed(effect: E, ctx): Bleed      // فضای لازم اطراف شکل
    fun describe(effect: E, ctx): PassDescriptor
    fun cost(effect: E): Int
}
```

پیامدها:

- **پنل تنظیمات دستی نوشته نمی‌شود.** از `parameters` تولید می‌شود. افکت جدید =
  رابط کاربری خودکار.
- **خط لولهٔ رندر هیچ افکتی را با نام نمی‌شناسد.** از رجیستری می‌پرسد.
- **افکت جدید یک فایل است + یک خط ثبت.** تست `a third-party effect can be
  registered without touching the pipeline` این را ثابت می‌کند.
- **تستی وجود دارد که اگر افکتی به مدل اضافه شود ولی ماژولش ثبت نشود، بیلد
  می‌شکند.** همان الگو برای حالت‌های ترکیب هم اجرا شده.

این الگو برای لایه‌های تنظیم، ابزارها و صادرکننده‌ها هم تکرار می‌شود.

## ۶. جمع‌بندی صادقانه

ایرادی که گرفتید درست بود، ولی نه دقیقاً به آن شکل: جداسازی بکگراند **در برنامه بود**
— با اولویت پایین و بدون عمق. مشکل واقعی، **نبودن محور کیفیت در کاتالوگ** بود.

با ممیزی، دو چیز پیدا شد که واقعاً غایب بودند: **نور استودیویی** (که خودتان حدس
زدید) و **فضای رنگ و دقت بیت** (که جدی‌تر است و همین حالا در کد اصلاح شد، چون
بعداً بازنویسی می‌خواست).

بقیهٔ دامنه‌ها پوشش داشتند ولی عمقشان تا سطح «ف» کامل نبود؛ چهارده مورد اضافه شد.

هیچ‌کدام از اینها نیازمند بازنویسی کد موجود نیست — به‌جز فضای رنگ، که به همین دلیل
همین حالا انجام شد.
